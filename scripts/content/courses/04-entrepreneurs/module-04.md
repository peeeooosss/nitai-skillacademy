### Module 1 · The MVP Trap: Overbuilding Is the Real Failure

The real MVP failure is not launching something too small - it is building too much before anyone pays. **MVP means the smallest thing that tests your riskiest assumption, not a mini version of the final product.**

AI makes building cheap, which makes overbuilding easier than ever. The discipline is to scope ruthlessly and ship fast.

## Learning Objectives

- Define an MVP by its purpose, not its size
- Identify your riskiest assumption
- Avoid the overbuilding trap AI makes easier
- Aim to ship a testable version fast

## What an MVP Really Is

- The smallest thing that tests your riskiest assumption
- Not a mini version of the final product
- Success is learning, not completeness
### The question
- What is the one belief that, if wrong, kills this?
- Test that first
- Everything else is later

## The Overbuilding Trap

- AI makes building cheap, so overbuilding is easier
- Polishing features no one asked for burns runway
- Months pass without a paying signal
### The warning
- 'Just one more feature' is the trap
- Complexity delays learning
- Ship, measure, then build
```text
Name my riskiest assumption for [idea] and the smallest
MVP that tests it in one week. List features to cut and the
single signal that would prove or disprove the assumption.
```

## Ship to Learn

- Aim to ship a testable version fast
- Measure behaviour, not applause
- Let evidence decide the next feature
### The payoff
- Faster feedback
- Less wasted code
- A real signal to act on

## Key Takeaways

- An MVP tests your riskiest assumption - it is not a small final product
- The real failure is overbuilding before anyone pays
- AI makes overbuilding easier; scope ruthlessly
- Find the one belief that, if wrong, kills the idea
- Ship, measure, then build

## Practice Challenge

1. Name your riskiest assumption
2. Define the smallest test for it
3. Cut every feature that does not serve that test

### Module 2 · Step 1: Scope the Leanest Version

Scope your MVP to one core promise: a single action a user takes that tests your assumption. List every feature, then cut everything that is not required for that one action.

Use the 'must do one job' rule. If your MVP tries to do three jobs, it does none well and tests nothing cleanly.

## Learning Objectives

- Define one core promise for the MVP
- List and cut features ruthlessly
- Apply the 'one job' rule
- Produce a buildable scope for one weekend or week

## One Core Promise

- One action a user takes that tests the assumption
- A single clear job
- Success measured by that action
### Why one
- Three jobs means none are tested cleanly
- Focus produces a clear signal
- You can always add later

## Cutting Features

- List every feature you imagined
- Mark what the one action truly requires
- Cut the rest without sentiment
### The rule
- If it is not required for the core action, it is later
- Features are hypotheses too
- Scope is the founder's discipline

## The Scope Prompt

```text
Scope the leanest MVP for [idea]: list features, then cut
everything not required to test [core assumption]. Give me a
one-weekend build plan with the single core action users take.
```
- One-weekend builds force honesty
- The core action is the target
- Everything else waits

## Key Takeaways

- Scope to one core promise and one user action
- List features, then cut everything not required
- If it does not serve the core action, it is later
- Three jobs means none are tested cleanly
- Produce a buildable one-weekend or one-week scope

## Practice Challenge

1. Write your one core promise
2. List all features and cut to the essentials
3. Produce a one-weekend build plan

**Example Quiz**

1. What should the MVP scope contain?
- A) One core promise and one user action
- B) Every feature
- C) Three jobs
- D) The final product

**Answer:** A — Scope to a single action that tests your assumption.

2. What do you do with extra features?
- A) Cut everything not required for the core action
- B) Build them first
- C) Keep them all
- D) Ask investors

**Answer:** A — If a feature is not required for the core action, it is later.

3. Why is one job better than three?
- A) Three jobs means none are tested cleanly
- B) It is cheaper
- C) It is prettier
- D) It is faster to code

**Answer:** A — Focus produces a clear signal; three jobs muddle the test.

4. What forces honesty in scoping?
- A) A one-weekend build plan
- B) A big budget
- C) A large team
- D) A long timeline

**Answer:** A — A weekend deadline forces ruthless scoping.

### Module 3 · Step 2: The Converting Landing Page (Weekend Build)

The landing page is your MVP's front door. Its only job is to convert a stranger into a signal - a sign-up, a reservation, or a pre-order.

Build it in a weekend with AI: one clear headline, one promise, one call to action. No clutter, no distractions, no second goal.

## Learning Objectives

- Write a one-promise headline
- Design a single call to action
- Build the page in a weekend with AI
- Optimise for one conversion, not many

## One Headline, One Promise

- Headline states the promise in the customer's words
- Subhead clarifies who it is for and what changes
- One promise only
### Why
- Clarity converts
- Multiple promises dilute
- The customer must know in three seconds

## One Call to Action

- A single action: sign up, reserve, or pre-order
- Button text says the action, not 'submit'
- Remove every competing link
### The rule
- One goal per page
- Fewer choices, more conversions
- The page's only job is the signal

## The Landing Prompt

```text
Write landing page copy for [idea]: a headline, subhead,
3 benefit bullets, and one CTA button. Audience: [customer].
Voice: simple, specific, no hype. Then give me a one-weekend
build plan with a tool like a no-code page builder.
```
- Simple, specific copy converts
- No hype - say the truth clearly
- A no-code builder keeps it a weekend job

## Key Takeaways

- The landing page has one job: convert a stranger into a signal
- One clear headline stating the promise in customer words
- One call to action; remove competing links
- Write simple, specific copy with no hype
- Build it in a weekend with a no-code tool

## Practice Challenge

1. Write your headline, subhead, and CTA
2. Build the page with a no-code tool
3. Get five people to react to it before launch

**Example Quiz**

**Answer:** A — Its only job is to produce a sign-up, reservation, or pre-order.

2. How many calls to action should it have?

- D) None

**Answer:** A — One goal per page; fewer choices convert better.

3. What should the headline do?
- A) State the promise in the customer's words
- B) Use jargon
- C) Be clever
- D) Be long

**Answer:** A — Clarity converts - the customer must get it in three seconds.

4. What tone should the copy use?
- A) Simple, specific, no hype
- B) Dramatic

- D) Formal

**Answer:** A — Say the truth clearly; hype undermines trust.

### Module 4 · Step 3: Capture the Signal (Lead, Pre-Order, or Waitlist)

A signal is only useful if you capture it. A like is not a signal; an email, a reservation, or a pre-order is. Choose the strongest capture your stage allows.

Strongest to weakest: **pre-order (paid) > reservation (committed) > waitlist (email) > like (noise).** Capture the strongest one you can honestly offer.

## Learning Objectives

- Rank signal types by strength
- Choose the strongest honest capture
- Set up a simple capture mechanism
- Store and use the data

## Ranking Signals

- **Pre-order (paid):** strongest - real money
- **Reservation (committed):** strong - intent plus action
- **Waitlist (email):** moderate - interest
- **Like (noise):** weakest - no commitment
### The point
- Commitment strength rises with cost to the user
- Paid beats promised
- Capture the strongest you can offer

## Choosing Your Capture

- Match the capture to what is honest at your stage
- A pre-order needs a clear promise and refund path
- A waitlist is fine when pre-ordering is not ready
### The rule
- Do not fake scarcity
- Capture, then follow up
- The list is an asset

## The Capture Prompt

```text
Design a simple capture for [landing page]: choose pre-order,
reservation, or waitlist, write the button and confirmation copy,
and list the fields to collect. Keep it to one screen.
```
- One screen, few fields
- Clear button and confirmation copy
- Store the data somewhere you own

## Key Takeaways

- Capture signals, do not just collect likes
- Rank: pre-order > reservation > waitlist > like
- Capture the strongest signal you can honestly offer
- Keep the form to one screen with few fields
- Store the data - the list is an asset

## Practice Challenge

1. Choose your signal type
2. Set up a one-screen capture form
3. Write the button and confirmation copy

**Example Quiz**

1. Which signal is strongest?
- A) Pre-order (paid)
- B) Waitlist
- C) Like
- D) Page view

**Answer:** A — Paid commitment is the strongest signal - real money at risk.

2. What makes a signal strong?
- A) The user's cost to commit
- B) Its colour
- C) Its font
- D) Its placement

**Answer:** A — Commitment strength rises with the cost to the user.

3. How many fields should the form have?
- A) Few, on one screen
- B) Twenty
- C) Ten
- D) As many as possible

**Answer:** A — One screen with few fields captures more signals.

4. What must you do after capturing?
- A) Store and follow up - the list is an asset
- B) Delete it
- C) Sell it
- D) Ignore it

**Answer:** A — The captured list is an asset you own and follow up on.

### Module 5 · Step 4: The 60-Second Demo (No Editing Skills Needed)

A 60-second demo explains your product without a live build. You can make one with a script, a screen recording, and free tools - no editing skills required.

The demo is for clarity, not polish. Show the core action, the before-and-after, and the promise in one minute.

## Learning Objectives

- Script a 60-second demo
- Record with free, simple tools
- Show the core action and before/after
- Use the demo to test understanding

## The Demo Structure

- 0-10s: the problem and who it is for
- 10-40s: the core action, shown simply
- 40-55s: the before-and-after
- 55-60s: the promise and call to action
### Why this order
- Problem first earns attention
- Showing beats telling
- The close asks for the signal

## Simple Tools

- A phone or screen recording
- A no-code page or slides as the backdrop
- Free editing is optional, not required
### The rule
- Polish is not the point
- Clarity is the point
- Ship the rough demo

## The Demo Prompt

```text
Write a 60-second demo script for [product] using a
screen recording and a no-code page. Show the core action
and the before/after. Plain language, no editing required.
```
- A script prevents rambling
- Plain language serves clarity
- No editing keeps it fast

## Key Takeaways

- A 60-second demo explains the product without a live build
- Structure: problem, core action, before/after, promise
- Use a phone recording and a no-code page
- Polish is not the point - clarity is
- Use the demo to test understanding

## Practice Challenge

1. Write your 60-second demo script
2. Record it with a simple screen recording
3. Test whether a stranger understands it

**Answer:** A — Use the demo to check that a stranger grasps the product.

### Module 6 · Step 5: Build vs No-Code Core

Most lean startups do not need custom code for the MVP. A no-code core - forms, pages, spreadsheets, automations - can test the assumption and even serve early customers.

Build custom only when the no-code path blocks the core action or your edge. Otherwise, no-code is faster and cheaper.

## Learning Objectives

- Decide when no-code is enough
- Map the no-code stack for your MVP
- Identify when custom code is truly needed
- Ship the fastest viable core

## When No-Code Is Enough

- Forms and pages for capture and delivery
- Spreadsheets or databases for records
- Automations for follow-up and admin
### Why
- It ships in days, not months
- It is cheap and changeable
- It tests the assumption fast

## When to Build Custom

- The no-code path blocks the core action
- The edge itself is the custom technology
- Scale or integration demands it
### The rule
- Build late, not early
- Prove demand first
- Code is the last resort, not the first

## The Core Prompt

```text
Map a no-code MVP core for [idea] using pages, forms,
a spreadsheet/database, and automations. Identify where
no-code is enough and the one place custom code might be
needed. Keep it shippable in one week.
```
- Map the whole core
- Flag the one custom need
- Keep it a one-week ship

## Key Takeaways

- Most lean MVPs do not need custom code
- No-code forms, pages, sheets, and automations can test the assumption
- Build custom only when no-code blocks the core action or your edge
- Build late, not early - prove demand first
- Ship the fastest viable core

## Practice Challenge
