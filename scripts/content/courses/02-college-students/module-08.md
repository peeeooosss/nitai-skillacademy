# Mission 8: Building an AI Mini-Project

## Learning Objectives
- Go from idea to shipped mini-project in one week
- Write a mini project brief and scope it realistically
- Build a small real product with the AI skills from Missions 1–7
- Test your project with real users and iterate
- Package and share it as a portfolio-worthy artefact

---
### Module 1 · The One-Week Project Method
A one-week build teaches more than a semester of theory. The method:

- **5 days, small scope.** You're aiming to *ship* — not to build the world's best anything.
- **Boring-but-real beats clever-but-mock.** A tool your hostel-mates actually use beats a hypothetical app.
- **AI is your workforce:** you direct it, it codes/drafts/designs, you own the quality.

The whole mission is a product sprint: scope Monday, build Tuesday–Wednesday, test Thursday, package Friday. Every day's output builds the portfolio piece you'll show in Mission 9.

**Example Quiz**

1. What is the goal of the one-week project method?
- A) Ship something real — not the world's best anything
- B) Build the perfect product
- C) Write a 100-page spec
- D) Impress with scope

**Answer:** A — Shipping beats grandiosity for learning and portfolio.

2. Why choose a 'boring-but-real' idea?
- A) Real daily problems yield used tools and learning
- B) Popular apps are easier
- C) Mock projects look better
- D) They are faster to clone

**Answer:** A — Boring real pain means actual users and real iteration.

3. What role does AI play in this sprint?
- A) Workforce: it codes/drafts/designs while you direct quality
- B) The decision maker
- C) The project owner
- D) The tester only

**Answer:** A — AI accelerates; you own scope, quality, and outcome.

### Module 2 · Day 1: Pick & Scope
Pick ONE idea that fits your slice:

- **Flashcard generator** from your notes.
- **Syllabus/assignment deadline tracker** that nags you.
- **Study-time splitter** (pomodoro with AI plans).
- **Weekly lecture summariser** for your course group.
- **Mini chatbot** that answers "where do I find X" for your college.

Scope it brutally: *"If I can't build a v1 in 3 days, cut the scope in half."* Write 3 user stories, decide the ONE flow that must work, and what "done" looks like. A half-scoped project that ships beats a grand one that doesn't.

**Example Quiz**

1. What is the Day-1 anti-scope trick?
- A) Cut the scope until v1 fits in three days
- B) Add every feature now
- C) Promise all users everything
- D) Plan for six months

**Answer:** A — A half-scoped project that ships beats a grand one that dies.

2. What must the core flow do on Day 1?
- A) The ONE thing that must work, clearly defined
- B) Everything at once
- C) Beautiful UI
- D) Nothing yet

**Answer:** A — Define the single must-work flow before building.

3. Define 'done' for a v1 means ________.
- A) that core flow works and is presentable
- B) feature-complete
- C) marketing ready
- D) zero bugs ever

**Answer:** A — A presentable, working core is the definition of done.

### Module 3 · Days 2-3: Build the Core
Build the single core flow first — everything else is a stretch goal:

1. **Skeleton:** let the AI scaffold the app or script for your one flow.
2. **Core function:** make the ONE thing work — input → processing → output.
3. **Error handling:** ask AI: *"What are the 5 ways a user could break this, and how do I handle them?"*
4. **Commit daily.** A working-but-ugly core on Wednesday night is a project you can present.

Resist the urge to add features. Feature creep is the #1 project killer — an unpolished core on Friday beats half-built extras.

**Example Quiz**

1. What order should Days 2-3 follow?
- A) Skeleton → one core function → error handling → daily commits
- B) Features → polish → skeleton
- C) Design → graphics → logic
- D) Everything at once

**Answer:** A — Core flow first; extras only after it works.

2. Why commit daily during the build?
- A) A working-but-ugly core each night is presentable
- B) It slows the build
- C) Git requires it
- D) It fills storage

**Answer:** A — Daily commits guarantee a presentable state at day end.

3. What is the #1 project killer?
- A) Feature creep
- B) Slow internet
- C) Small fonts
- D) Too many commits

**Answer:** A — Adding options before the core works kills projects.

### Module 4 · Day 4: Real-User Test (Even One Friend Counts)
Ship to a real human before you call it done:

- Give it to **one friend or classmate** with zero explanation.
- Watch (don't coach) them use it. Note where they hesitate or give up.
- Ask 3 questions: *What did you try first? Where did you get stuck? Would you use this again?*

"Works on my machine" is not a product. Even a 10-minute test with one person surfaces the fix that makes the difference between a folder and a project.

**Example Quiz**

1. Why test with a real user—even one friend?
- A) They surface friction you cannot see yourself
- B) It is a formality
- C) It is the last step
- D) To collect emails

**Answer:** A — Uncoached observers reveal real hesitation and drop-off.

2. What three questions define a valid test?

- B) Who is your favourite? Is it colourful? Is it fast?
- C) Did you like the logo? The theme? The font?
- D) Do you have time? Money? Interest?

**Answer:** A — Observation plus those three questions is a real test.

3. What is the outcome of a 10-minute test?
- A) Concrete fixes that turn a folder into a project
- B) Confirmation everything is perfect
- C) A launch
- D) Feature requests only

**Answer:** A — Small tests yield the fixes that matter most.

### Module 5 · Day 5: Package & Share
Package it like it matters — because it will be your portfolio:

- **README:** what it does, how to run it, one screenshot.
- **Demo:** a 60-90 second screen recording walking the core flow.
- **Deploy:** if it's a website/app, put it somewhere a link opens (free tiers: Netlify, Streamlit, Colab, GitHub Pages).
- **Share:** post it in your course group and on LinkedIn — feedback is the point.

A packaged project with a real user is 10x your recruiting story. The packaging is the work.

**Example Quiz**

1. What should the README contain?

**Answer:** A — A caller must run it from the README alone.

### Module 6 · The Reflection Loop (What Makes It Portfolio-Worthy)
After shipping, run the reflection that makes projects impressive:

- **What I built** (one line) and **why it matters** (to whom).
- **Hardest technical problem** — the error or gap that cost the most time, and how you solved it.
- **What I'd improve** with 2 more weeks (shows judgment, not failure).
- **AI's exact role** — which parts AI did, which you did, and why.

This 5-minute reflection becomes your case study in Mission 9. Never skip it — it's the difference between "I built a thing" and an interview story.

## Real-World Examples

- A commerce student ships a 'timetable clash finder' script used by 12 hostelmates within a week.
- A journalism student builds a 'daily headlines digest' bot for their class group.
- A teacher-trainee creates an AI flashcard generator from her teaching notes and tests it on a friend.
- An engineering student packages a lab-data cleaner as a tiny web tool on Streamlit and posts it publicly.

## Key Takeaways
- One week, one user, one problem: scope to a sentence.
- MVP: input → AI brain → output → one polish pass.
- Test with real users early; you'll learn what's actually broken.
- Package it: README + demo + honest AI-use note.
- Write the reflection — that's what turns a toy into a portfolio piece.

## Practice Challenge
1. **Day 1:** Write your one-paragraph project brief and the "My project helps ___ do ___" sentence. Get it approved by a classmate or mentor.
2. **Day 2–3:** Build the working MVP (input → AI → output). Run it on at least 3 test inputs.
3. **Day 4:** Get 1+ real user to try it. Collect their 3 feedback answers, fix the top 2 issues.
4. **Day 5:** Publish the README + 60-sec demo + honest AI line somewhere shareable (GitHub, a doc, or a video link). Submit the shareable link + your 5 reflections as the mission assignment.
